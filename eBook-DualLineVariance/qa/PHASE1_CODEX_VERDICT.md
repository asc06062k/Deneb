## 1. Verdict: REVISE

แนวคิด crossing-case และสูตร interpolation สอดคล้องกับ `segmentFill.ts` ในระดับอัลกอริทึม และ prototype แสดงว่า `area + detail: run_id` เป็นแนวทางที่เป็นไปได้ใน Vega-Lite

อย่างไรก็ตาม Design Plan ยังมี Mandatory findings สำคัญ โดยเฉพาะโครงสร้าง dataset จริงสำหรับ fill/line ที่มีคนละ grain, defensive policy ของ `Business_Type`, Test matrix ที่ยังไม่ตรงกับข้อกำหนดใน `PROJECT_PLAN.md`, การเพิ่ม `KPI_ID` โดยไม่มีความจำเป็นพิสูจน์ได้ และ accessibility claim ที่ยังเกินหลักฐาน

## 3. Optional improvements

- สูตร crossing สอดคล้องกับ `segmentFill.ts`: เงื่อนไข `d0*d1 < 0`, ค่า `t = d0/(d0-d1)` และ linear interpolation ตรงกัน โดย source คำนวณใน pixel space ส่วน Design Plan คำนวณใน value space ซึ่งให้ตำแหน่งเดียวกันเมื่อใช้ linear scales เท่านั้น ควรเขียนข้อจำกัดเรื่อง linear X/Y scale ไว้ชัดเจน
- เพิ่ม test สำหรับช่วงที่ปลายด้านหนึ่งมี `diff = 0` แล้วอีกด้านเป็นบวก/ลบ เพื่อยืนยันการรวม run รอบจุด equality ไม่เกิดช่องว่างหรือการจัดสีผิด
- `Sort_Order` ไม่เพียงต้องเป็นตัวเลขและ unique แต่ถ้าต้องเลียนแบบ `scalePoint` เดิมด้วยระยะเท่ากัน ควรกำหนดให้ต่อเนื่องหรืออธิบายว่าช่องว่างของเลขจะกลายเป็นระยะห่างจริงบน quantitative scale
- ระบุว่า `labelOverlap: "greedy"` อาจตัด label สุดท้ายออก ขณะที่อัลกอริทึมต้นแบบบังคับแสดง Category สุดท้าย จึงต้องมี test หรือ logic เพิ่มหากต้องการเทียบเท่าพฤติกรรมนั้น
- เปลี่ยนข้อความ “บทที่ 9 และ 11” เป็น “บทที่ 9 และ 10” หรือบทที่เกี่ยวข้องจริง เพราะโครงสร้างหนังสือมี 10 บท
- คำว่า Format pane สำหรับแก้สีควรยืนยันว่าเป็นกลไกที่ Deneb 2.0.0.0 เปิดให้ template นี้ใช้จริง ไม่ควรเทียบตรงกับ custom visual formatting object จนกว่าจะมี prototype

## 4. คำถามที่ต้องรอหลักฐานจาก Phase 2

1. Dataset จริงจะเก็บ original rows และ crossing rows อย่างไร โดยไม่ทำลาย grain, line marks, tooltip, cross-filter และ context-menu resolution?
2. เมื่อ slicer/filter ทำให้ Actual หรือ Reference เปลี่ยน ค่า crossing ที่ Power Query precompute ไว้ยังถูกต้องหรือไม่ หรือ Workshop จะประกาศไม่รองรับกรณีนี้?
3. `Business_Type` Measure ปรากฏใน Deneb `dataset` หนึ่งค่าต่อ Category จริงหรือไม่ และชื่อ field ตรงตามที่ spec อ้างหรือไม่?
4. การเลือกค่าของแถวแรกที่ valid ตาม `Sort_Order` และ QA warning เมื่อพบหลายค่า implement ได้อย่างไรใน spec จริง?
5. `width: "container"` หรือ `autosize.fit + resize` วิธีใดทำงานจริงใน Deneb 2.0.0.0 และ Vega/Vega-Lite version ที่ Deneb ฝังมา?
6. Category lookup/`labelExpr` แบบ dynamic ทำงานกับ 24+ Category, ข้อความยาว และ resize จริงหรือไม่?
7. Actual/Reference data-label thinning ถูกประเมินใหม่ทุกครั้งที่ resize จริงหรือไม่ และ formula ใช้ความกว้างข้อความจริงหรือเพียงค่าประมาณ?
8. 280×180px ผ่านทั้งเกณฑ์ axis collision-free และ data-label “ลดการชน” ในชุด long+dense หรือไม่?
9. Good/Bad ยังแยกได้โดยไม่พึ่ง hue ภายใต้ CVD simulation และเมื่อ area ใช้ opacity จริงหรือไม่?
10. ชื่อและตำแหน่ง UI ของ cross-filter, cross-highlight, Supporting Fields และ Context menu ตรงกับ Deneb 2.0.0.0 จริงหรือไม่?

สรุป: แกนความคิดทางเทคนิคของ crossing-case ใช้ได้ แต่ Design Plan ยังไม่พร้อม PASS จนกว่าจะปิด M-01 ถึง M-10 หรือปรับขอบเขต/คำสัญญาให้ตรงกับหลักฐานที่มีอยู่จริง.
